# World Event Entity Schema

**Schema Version**: 2020-12 (JSON Schema) | **Entity Type**: world-event | **Last Updated**: 2026-10-30

## Baseline required fields

The baseline validator accepts historical IDs and events without `geo`. New published events use Snowflake IDs and the additional qualified-event rules below.

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| `id` | string | minLength: 8 | Unique event identifier. New output uses Snowflake format `evt_<snowflake>` (e.g. `evt_52117619469189120`), generated by `data/scripts/snowflake.js`; baseline validation also accepts legacy IDs. |
| `source` | object | required: `name` | Origin of event; optional: `provider`, `email` |
| `title` | string | minLength: 3 | Event headline |
| `summary` | string | minLength: 10 | 2–4 sentence narrative summary |
| `contents` | string | Baseline: ≥20 characters; qualified: ≥100 prose words and **E-PRIME** | Evidence-grounded Markdown event description |
| `date_published` | ISO 8601 | Baseline accepts a timezone offset; qualified output uses UTC `Z` | When the source published the event |
| `links` | array | `[{url, label?}]` | Source URLs |
| `image_urls` | array | `string[]` | Remote image URLs. New qualified events require at least one; historical events may have `[]` or legacy relative paths. |

> **Validator**: `data/scripts/validate-events.js --qualified` for newly published events. Baseline and `--strict` remain available for historical records. Both runtime prompts invoke `--qualified` before committing.

## New qualified-event fields

New output adds these typed fields to the base entity. Historical JSONL does not need migration.

| Field | Type | Requirement |
|-------|------|-------------|
| `geo` | object | Required geographic context with numeric `lat` and `lon`; may also include `country`, `region`, and `city`. |
| `source_window` | object | `{start, end}` UTC timestamps from the candidate's original scan window; `date_published` must fall inside. |
| `language` | literal `"en"` | Title, summary, and contents translated fully into English. |
| `category` | enum | `armed-conflict`, `geopolitics`, `defense`, `electronic-warfare`, `major-disaster`, `civil-unrest`, `maritime-security`. |
| `audience` | enum | `united-states` or `allied-forces`. |
| `allied_relevance` | string | Concrete situational-awareness value for that audience. |
| `image_origin` | enum | Describes `image_urls[0]`: `article` for event/article imagery, `source` for a source banner/logo, `default` for the public site icon. These labels prevent a fallback image from posing as event evidence. |
| `geo.location_name` | string | Named location represented by the point. |
| `geo.precision` | enum | `exact`, `city`, `region`, `country`, or `sea-area`. A broad report uses an honestly labeled centroid; unlocatable reports get rejected. |

Qualified `contents` uses five nonempty H2 sections in this order: `Event`, `Location and Time`, `Evidence`, `Allied Relevance`, `Confidence and Gaps`. It contains at least 100 evidence-grounded prose words, with no E-PRIME contractions, HTML, or HTML entities. An accepted event needs at least one remote HTTP(S) source URL and a verified image URL. Enrichment may choose `https://osint.builders/favicon.svg` only as a clearly marked `default` image. Coordinates `(0, 0)` and the former San Francisco global fallback cannot represent an unknown location. Candidate acceptance also requires a concrete new OSINT development with allied relevance; `--qualified` checks typed declarations and mechanical constraints, while the agent must judge the underlying evidence. Single-source claims must remain attributed throughout the text. Every independent source used to call a claim confirmed or corroborated belongs in `links`; a conflict party and its affiliated outlets count as one evidentiary line. A multi-country story with no source-supported focal location or bounded area has no valid single `geo` point and must be rejected.

## Optional Fields

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| `date_event` | ISO 8601 or null | `YYYY-MM-DDTHH:mm:ssZ` | When the event occurred (precedes or equals `date_published`) |
| `topics` | array | `string[]` | Lowercase, hyphenated, singular keywords |
| `confidence` | number | 0.0–1.0 | Data quality score (0.8–1.0 = high, 0.0–0.2 = unverified) |
| `ingested_at` | ISO 8601 | `YYYY-MM-DDTHH:mm:ssZ` | Ingestion timestamp; auto-generated |
| `link_preview` | object or null | `{title, description, image, url}` | Cached link preview from `links[0]` via LinkPreview API; `image` is an OG image URL |

Temporal order: `date_event ≤ date_published ≤ ingested_at`

  "title": "Illustrative Port Closure During Regional Storm",
  "summary": "An illustrative maritime authority closes a major port after a regional storm disrupts vessel traffic. This fictional record demonstrates the qualified-event format.",
  "contents": "## Event\n\nAn illustrative maritime authority closed a major port after a regional storm disrupted vessel movements and damaged several berths. ## Validation rules

- Baseline: required fields in the first table; `id` accepts Snowflake or legacy `evt_YYYYMMDD_NNN` format, `contents` needs at least 20 characters, and `geo` may be absent. If coordinates exist, latitude must fall within −90 to 90 and longitude within −180 to 180.
- `--strict`: requires numeric `geo.lat` and `geo.lon` and enforces E-PRIME in `contents`.
- `--qualified`: adds the typed fields, image, ≥100 prose words, and body structure above for new output. Historical records retain baseline validation.
- `source`: object with `name`
- `title`: ≥3 chars
- `summary`: ≥10 chars
- `date_published`: valid ISO 8601 timestamp
- `links`: array; items have required `url`
- `image_urls`: array; qualified output requires a remote image and `image_origin`
- `confidence`: 0.0–1.0 if present
- No HTML in text fields (Markdown code blocks excepted)

## Storage Format

**JSONL** — one JSON object per line in `data/events/YYYY-MM/YYYY-MM-DD.jsonl`. Merge and dedupe steps may rewrite a daily file; the weekly retention sweep deletes old daily files.
